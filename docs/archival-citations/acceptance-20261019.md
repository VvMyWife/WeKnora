## 发现并解决的问题

1. 第一次镜像继承了私有构建目录的 700 权限，迁移器作为 appuser 无法读取 SQL。应用 `/health` 仍返回正常，所以立即回退并修复 Dockerfile 目录／文件权限；增加 appuser 读权限检查及干净迁移版本检查，再发布。
2. nginx 缺少 `.mjs` 的 JS MIME，开发服务器通过而正式 PDF worker 无法加载。回退 custom 后，修正两个 Dockerfile 并重新发布。正式响应已为 `application/javascript`。
3. 恢复历史快速问答时事件数组被 markRaw；校验完成后原地 push 不能触发正文更新。改为替换数组引用，回归和无需刷新真实提问均通过。

如果浏览器曾加载本次修正前失败的 worker，可能命中旧静态 MIME 缓存，需强制刷新一次（Ctrl+F5）。此后新请求使用正确 MIME；普通脚注和历史记录不依赖外部 CDN。

## 不夸大的验收边界

- 引用绑定只验证“来源确实提供给了模型、版本与内容可追溯”，不自动证明模型的每个事实／推理都正确。本次普通问答首次把两条事实绑定同一 chunk，清单如实保留实际绑定；严谨使用时仍应核对快照。
- 有些引言或仅写普通 `[1]`、未就近绑定真实 `<kb>` 的条目会标注“未绑定来源”。一次补引没有成功时不伪造关联、不改写事实；样例中 `needs_review` 是明确提示，不是保存失败。后续短句测试无需补引，显示 verified。
- Wiki／图谱派生追溯、共享权限撤销、原件换版／删除等边界已由后端回归和隔离页面验证，没有对正式库做破坏性演练。业务图谱／Wiki 全量来源质量、超大 PDF 性能和模型事实正确性不是本次已证明的结果。
- 旧消息未事先保存引用版本时明确提示“历史回答没有版本化引用记录”；不后台补写、猜页码或重跑旧档案。
- 正式库历史失败和处理队列未批量重试；功能上线不等于这些旧任务被修好。
